## 1. 背景

### 1.1 业务问题

电商公司的运营、投放、品类经理每天会问大量指标问题:

- **查数类**:「上周美国站 GMV 是多少?」「上周各渠道的订单量?」
- **归因类**:「上周 GMV 为什么跌了?是流量、转化还是客单价的问题?主要跌在哪个渠道?」

这些问题今天靠数据团队人工写 SQL 回答。查数类占用大量零碎时间,归因类人工排查通常要 1~2 天。

### 1.2 为什么不能直接「让 LLM 写 SQL」

大模型写 SQL 已经不难,难的是另外两件事:

1. **怎么知道它答对了?** SQL 能跑通、返回了数字,不代表数字是对的。
   用错口径(比如把退款订单也算进 GMV)、用错日期(用了真实世界的「今天」去查历史数据),
   都会得到一个**看起来很正常的错数字**。错的数字会直接影响投放预算。
2. **怎么让它持续变好,并且证明是真的变好?** 改了 prompt 之后准确率变了,
   是改动的作用,还是评估集太小带来的波动?改动会不会只是「背答案」?

### 1.3 项目定位

本项目的首要目的,是用一个完整、可运行的系统展示 **loop engineering**:
系统能自己发现问题、自己验证、自己取舍,并且**下一轮会读取上一轮写下的状态**。

判据(贯穿全部设计):**只写不读的定时任务是复读机,不是循环。**

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | 归因结论**可验证**:各部分贡献之和必须等于总变化 | 分解残差 < 0.1% |
| G2 | 查数结果**可评估**:有不依赖人工标注的标准答案 | 评估集 26 题,标准答案程序化生成 |
| G3 | 系统能**自我修复**:一次提问内,写错的 SQL 能根据具体反馈改对 | 最终准确率 − 首轮准确率 |
| G4 | 系统能**自主改进**:跨版本地发现错题、提出改进、验证、取舍 | 迭代曲线 + 台账 |
| G5 | 改进**不能背答案、不能靠拒答刷分** | 留出集、不可答对照组、误拒率 |
| G6 | 跑在 **Databricks** 上,并能作为可用的问答工具上线 | notebook / 网页 / 定时任务三个入口 |

### 2.2 非目标

- 不做通用 BI 或任意数据源接入:只针对一个电商数仓的五张表
- 不追求 SQL 生成的 SOTA 准确率:模型用的是免费的 `glm-4-flash`,重点在循环而不是模型
- 不做对话式多轮追问:每个问题独立回答
- 不引入 LangChain / 向量数据库 / Airflow:它们会把重试、检索这些关键逻辑藏起来,而本项目恰恰要把这些逻辑摊开

## 3. 用户与场景

| 角色 | 想做什么 | 入口 |
|---|---|---|
| **业务提问人**(运营、投放、品类经理) | 问数、问原因,拿到可信的答案 | 网页聊天 / notebook `05` |
| **数据团队(维护者)** | 维护指标口径、复核答错的问题、决定是否合并改进 | YAML 知识库、待复核队列、Git PR |
| **系统自身(定时任务)** | 每天评估、每周改进、每周自动出归因结论 | Databricks Jobs |

### 用户故事

- **US-1** 作为运营,我问「上周美国站 GMV 为什么下降」,希望知道是流量、转化还是客单价导致的,
  以及贡献最大的渠道或品类,并且**看得到每个数字背后的 SQL**。
- **US-2** 作为投放经理,我问「上周各渠道 GMV 是多少」,希望直接拿到表格。
- **US-3** 作为业务人员,我问了数据里没有的东西(比如毛利率),希望系统**明确说答不了**,而不是编一个数。
- **US-4** 作为数据团队,我希望看到系统答错的问题,确认口径后把它变成新的考题。
- **US-5** 作为数据团队,我希望系统自己提出 prompt 改进,但**只有经过验证、不退步的改进才能合并**,并且合并要经过我 review。
- **US-6** 作为评审者,我希望看到任何一次准确率变化,都能说清楚是哪个改动带来的。

## 5. 非功能需求

| 编号 | 类别 | 要求 | 做法 |
|---|---|---|---|
| NFR-1 | **正确性** | 归因数字必须对得上账 | 分解内核保证闭合;残差作为可信度展示给用户 |
| NFR-2 | **可复现** | 每个数字能回溯到 SQL;每次评估能回溯到 prompt | SQL 指纹;prompt 指纹;确定性解码(`do_sample=false`) |
| NFR-3 | **安全** | LLM 生成的 SQL 不能改数据 | 守卫只放行只读查询;线上服务的数据库账号只有读权限(加写日志) |
| NFR-4 | **凭据** | 密钥不进代码、日志、URL、Git | 只从 Databricks secret / 环境变量读;`repr` 打码;测试断言不泄漏 |
| NFR-5 | **成本** | 免费额度内可运行 | 调用预算熔断;prompt 缓存;标准答案只算一次;空话不试跑 |
| NFR-6 | **平台** | 跑在 Databricks Free Edition | serverless;默认 catalog `workspace`;`/Workspace` 不写字节码缓存 |
| NFR-7 | **可测试** | 改代码后秒级回归 | 同一套测试可跑在 DuckDB(本地)和 Spark(Databricks)上 |
| NFR-8 | **可维护** | 业务口径与代码分离 | 指标、维度、提示、业务词表都在 YAML;改它们不需要改代码 |

## 6. 与原始简报的差异

项目起点是《项目简报》(仓库外的原始规格)的 V0(建表 + 指标树 + 确定性分解 + 闭合性测试)。
V0 全部完成后,根据求职展示的需要调整了方向:**用 text-to-SQL 加上它的评估与改进,来展示 loop engineering**。
由此产生两处与简报约束的差异,如实记录:

| 简报约束 | 现状 | 理由与缓解 |
|---|---|---|
| §5「LLM 不得生成 SQL」 | **查数路径**由 LLM 生成 SQL | 查数的问题形式是开放的,无法穷举成模板。缓解:守卫只放行只读查询并校验表列白名单;执行式比对 + 程序化标准答案持续评估;**归因路径仍然完全遵守这条约束**,不经 LLM |
| §4.2「不调用外部 LLM API」 | 使用智谱 `glm-4-flash`(外部) | workspace 没有可用的 Foundation Model 端点。客户端只认 OpenAI 兼容格式,换回 workspace 内端点只需改配置;LLM 密钥存在 Databricks secret |

简报中 V1~V4 的内容(合成异常注入、LLM 选择钻取维度、跨天异常台账、MLflow Tracing)**没有实现**,见第 9 节。

## 7. 评估指标定义

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| 最终准确率 `pass_final` | 可答题中,最终结果与标准答案一致的比例 | 主指标 |
| 首轮准确率 `pass@1` | 可答题中,第一次就答对的比例 | 与最终准确率之差 = 自修复的贡献 |
| 平均轮数 `avg_attempts` | 每题平均尝试次数 | 自修复的成本 |
| 幻觉率 | 引用了不存在的表/列的题目比例 | 编造的一种可测量形式 |
| 正确拒答率 | 不可答题中正确拒答的比例 | 会不会在没有依据时编答案 |
| 误拒率 | 可答题中拒答的比例 | 防止「一律拒答」刷高正确拒答率 |
| 训练集 / 留出集准确率 | 可答题答对 + 不可答题正确拒答,分别按训练集、留出集计算 | 改进循环的目标与防过拟合闸门 |
